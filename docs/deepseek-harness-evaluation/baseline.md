# DeepSeek Harness 行为与权限基线

- 建立日期：2026-10-11
- 来源：用户提供的 Harness 桌面版截图和本次确认的要求。
- 版本号、插件能力、持久化配置、GitHub API 运行结果：**尚未核验**。
- 记录性质：目标基线（EXPECTED）与截图观察（REPORTED）分开，不把提示词当成已落地的技术强制策略。

## A. 授权边界（EXPECTED）

| ID | 规则 | 自动化期望 |
|---|---|---|
| AUTH-001 | 仅解决 `burncloud/burncloud` 中由 GitHub 登录用户 `rustburn` 创建的 Issue | 其余作者的 Issue 只读并跳过，不分配、不修复、不关闭 |
| AUTH-002 | 仅 `rustburn` 创建且全部实际代码贡献经核实属于 `rustburn` 的 PR 有自动合并资格 | 其他作者、混合贡献、来源不明的 PR 必须由人类决定 |
| AUTH-003 | PR 合并必须经过最新 HEAD 必需 CI、Review、合并冲突、分支保护和验收门禁 | 缺失、等待、失败或旧 SHA 均不通过 |
| AUTH-004 | 大型父 Issue 可由多个独立、完整验收的增量 PR 交付，仅当现行规则允许时执行合并 | 不因增量 PR 合并而提前关闭父 Issue；不得擅自变更合并规则 |
| AUTH-005 | 定时任务无人值守 | 不调用交互式问题；需要人工处理则记录并跳过 |
| AUTH-006 | 多 Agent 安全隔离 | 不共享写入分支、不覆盖别人成果、不以 force push 抢占 |
| AUTH-007 | P0 CI 冻结与本地执行边界 | 不改 CI，不在本地编译或执行单元测试 |

以上为期望目标。需要检查实际 Harness 定时任务配置、项目指令加载与 GitHub 权限，才能判定已落实。

## B. 初始观察（REPORTED；非 GitHub 独立验证）

1. Harness 桌面版截图显示权限选择为“完全权限”，但仍出现决策弹窗。权限模式不能等同于无人值守决策策略。
2. 并发开发过程中，Harness 报告存在另一写入者 force-push 到同一分支，随后请求用户决定是否让出 M01；截图显示改做不重叠 M06。
3. 定时管理巡检日志显示连续五轮状态不变（Rounds 20–24），随后仍调用用户选择，未自动结束本轮。
4. 截图中 Harness 自述 PR #869、#871 为 `rustburn` 作者、4/4 CI green，且涉及大型父 Issue #633/#634；Harness 因“PR 必须完全关闭关联 Issue”的条件暂停并请求是否允许 `Refs`-only 增量。**未独立验证最新 HEAD、真实 CI、实际作者/贡献者、Review、验收或可合并性。**

## C. 尚待确认

- 定时任务是否真的持久保存无人值守规则。
- 在桌面程序关闭、网络断开、重复调度时的行为。
- 是否支持禁用 `ask_user_question` 工具；仅靠提示词无法保证硬性禁止。
- PR #869/#871 的当前状态与真实 GitHub 证据。
- 白名单过滤是否在任务分配前及合并前分别验证。
- 是否有实际的历史非 rustburn 任务尚在执行。

## D. 对照原则

每次修改配置、提示词、Harness 版本或插件后，在 `runs/` 新建一份执行记录，对 `test-cases.md` 中同样用例重新核验；不能用“没有弹窗”单独判断整套管理系统合格。
