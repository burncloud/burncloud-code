# DeepSeek Harness定时任务的工作选择与互斥规则

## 定位

本文件是03代码开发定时任务的执行规则，不是新派发系统、独立Agent、后台进程或外部事件服务。只使用已经验证可用的Harness能力和Issue/PR协议留言及真实原生互斥证据。

## 选择工作

1. 03定时触发后检查自己的上轮运行状态；仍在运行时结束本轮。
2. 按留言协议读取Issue的02 PLAN_READY，以及关联PR中04/05/09的审查、CI或恢复留言。
3. 重核目标仓库、rustburn原始创建者身份、开放Issue、关键依赖和实际远端HEAD。
4. 优先续接自己的已有PR修复，再处理新的授权计划，保留排队时间避免长期饥饿。
5. 核验唯一写入者、文件范围与独立分支。其他负责者仍有效或互斥无法核验时不写入。
6. 唯一写入权成立后在Issue发布DEVELOPMENT_STARTED，绑定计划版本、分支与互斥证据，再修改代码。

同一Issue/PR只有一个有效开发负责者。本基础模式不要求多个常驻worker、独立状态DB、队列、事件邮箱或后台心跳。跨任务保护必须使用已核验的Harness原生互斥能力；缺失时阻塞相关写入，不以普通GitHub评论假装原子锁。

## 连续执行与续接

有工作时03在本轮推进可执行步骤；等待CI/Review时保存事实和检查点并结束，下次定时触发主动检查。可用的Harness会话恢复能力可以续接原会话，没有该能力时按Issue/PR检查点留言和远端分支继续，不重复创建PR。

04/05在PR发布REVIEW_RESULT/CI_RESULT即可完成交接，不要求即时调用其他Agent。多个同HEAD故障由03合并处理，引用全部直接输入comment ID；处理前再核验SHA，旧HEAD只归档。

## 预算与恢复

源码同根因自动修复默认最多3轮，临时CI故障最多重跑1次，自动恢复同故障最多1次；计数沿修复链累积，不能因新HEAD重置。

09根据Harness实际运行信息和远端事实确认停止，不能仅凭定时触发延迟或缺少未配置的心跳就抢占。原负责者未确认停止时不重新分配。

## 权限与记录

计划来自02，源码修改归03，审查归04，CI重跑归05，合并归06。仅使用已有授权；禁止本地编译/测试、修改CI、覆盖他人成果、泄露凭据或关闭外部Issue。

每次记录仓库、Issue/PR、计划版本、负责者、分支、文件范围、当前HEAD、去重键、实际动作、结果、修复次数和下一动作。无法保存或核验关键事实时明确阻塞，不宣称已经派发或恢复。

协议、共同配置及消息去重规则见[communication-protocol.md](communication-protocol.md)。排队的工作仍在Issue/PR留言中，不建立隐藏队列；本地缓存丢失后重读留言和真实远端状态。累计预算按repair_chain_id沿留言链恢复，不能确定时阻塞。
