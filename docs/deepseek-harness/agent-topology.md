# DeepSeek Harness Agent 角色与交接

## 调度模型

调度器负责周期触发、持久化去重、原子租约和重入控制。总调度负责范围、文件归属和角色交接。两者是 Harness 的运行前提，不新增编号任务，不自行开发第二套调度器，也不能假设这些能力已经存在。

11 个任务形成以下交接关系；顺序编号便于复制与排序，不要求所有任务严格串行执行。

| 编号 | Agent | 唯一负责动作 | 交接对象 |
|---|---|---|---|
| 01 | Issue 自动巡检 | 只读发现、白名单核验和分类 | 02 |
| 02 | 任务规划 | 原子认领、依赖和文件归属、验收计划 | 03 |
| 03 | 代码开发 | 独占分支源码与测试、提交 PR、源码修复 | 04、05 |
| 04 | PR 审查 | 需求和 Diff 审查、提交审查意见 | 03 修复；06 审查证据 |
| 05 | CI 守护 | 当前 HEAD 诊断、有限远端重跑 | 03 修复；04、06 CI 证据 |
| 06 | PR 合并控制 | 重新核验全部门禁、绑定 HEAD 合并 | 07、10 |
| 07 | Projects 管理 | 授权项目项既有自动化字段同步 | 持久化同步结果 |
| 08 | Harness 运行观察 | 只读观察健康、重入与权限违规 | 09、11 |
| 09 | 故障恢复 | 核验原负责者后恢复租约与交接 | 原负责 Agent、11 |
| 10 | 验收记录 | 维护指定验收文档和真实证据 | 07、11；已有授权的关闭流程 |
| 11 | 问题日志 | 去重维护指定问题文档 | 对应负责 Agent |

## 开发与修复闭环

01 发现候选项；02 再核验并安全认领；03 开发并推送。04 与 05 可以独立读取同一当前 HEAD。代码问题只交回 03；CI 环境问题只记录或由 05 有限重跑。新推送使原 HEAD 审查和 CI 证据失效，再进入 04/05。

06 在全部门禁通过后重新读取真实状态，以预期 HEAD SHA 执行受保护合并。合并结果经 GitHub 和目标分支核实后交给 07/10。07 的“完成”必须有最终验收证据，不能因 PR 合并就标记整个父 Issue 完成。

08 持续观察；09 只恢复安全调度和交接，不代替 03 改代码或代替 06 合并。10/11 在文档仓库的独立分支维护各自指定文件，不与源码分支竞争。

## 写入与权限边界

- 同一 Issue、PR、分支或文档文件同一时间只有一个有效写入者。
- 02 负责认领；01 不认领，09 只在确认原负责者停止后恢复租约。
- 03 负责源码和测试；04/05 不写源码，06 不修冲突，09 不改源码。
- 05 负责诊断和有限重跑；03 不改 CI，09 不重复重跑。
- 06 是唯一合并角色，且只在已有用户授权内操作；不得管理员绕过或延迟自动合并。
- 07 只同步既有自动化管理字段；10/11 只提交指定记录文档。
- 所有角色禁止本地编译和测试、修改 CI、覆盖他人成果或关闭外部 Issue。

## 交接数据

每次交接包含：仓库、Issue/PR 链接、范围、唯一负责者、租约、分支、当前 HEAD SHA、实际动作、证据链接、状态、阻塞原因、下一动作及去重键。

写操作前重新查询 GitHub，不依赖上轮缓存。缺少原子锁、持久化、权限或证据时暂停该对象写入，继续其他无依赖冲突任务。连续无变化时结束本轮，不重复评论或询问。

## Issue 关闭边界

合并 PR 与关闭 Issue 是两个不同动作。本集合不自动执行关闭。10 仅输出全量验收是否满足及关闭核验材料；已有明确授权的关闭流程仍须重核原始创建者、所有子任务、最终验收与真实 GitHub 状态。大型父 Issue 的部分交付不得触发关闭关键字。
