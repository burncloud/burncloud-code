# DeepSeek Harness 验收记录

## 目的与记录边界

记录中文定时与事件任务集合的验收标准及真实运行证据。本文件由 `10-test-case-recorder.md` 维护；不另建 `testing/` 路径，也不是独立定时任务 Prompt。

以下是验收设计，初始状态均为“未执行”。文档内容检查不等于 Harness 运行验收或 GitHub CI 通过。现有[行为回归用例](../deepseek-harness-evaluation/test-cases.md)与[运行档案](../deepseek-harness-evaluation/runs/)继续保留。

## 定时基础模式与可选事件验收

ST-20至ST-28中涉及事件邮箱、Webhook、worker槽或后台心跳的场景仅适用于另行启用且实际具备该能力的增强模式，不作为原生定时任务的强制前提。基础模式由ST-01和ST-33核验。

| 编号 | 场景 | 预期结果 | 初始状态 |
|---|---|---|---|
| ST-19 | 无变化的周期触发 | 只做增量对账，尽快结束、不继续加载全部历史，不重复评论或文档PR；不承诺零模型调用 | 未执行 |
| ST-20 | 派发事件重投递、worker忙碌 | 保留原会话和分支，消息入持久邮箱，不创建第二worker | 未执行 |
| ST-21 | 两个活跃worker且有新任务 | 新任务排队；等待CI释放执行槽但保留归属 | 未执行 |
| ST-22 | Webhook缺签名、无效签名或仓库不符 | 拒绝投递，无模型、修复或越权写入 | 未执行 |
| ST-23 | 同一CI失败Webhook与轮询同时到达 | 业务去重和修复租约只产生一条修复链 | 未执行 |
| ST-24 | 多个Workflow同一HEAD失败 | 合并日志到原会话邮箱，不竞争写分支 | 未执行 |
| ST-25 | 旧HEAD失败迟到、旧attempt重投递 | 只归档，不覆盖新成功、不修旧分支 | 未执行 |
| ST-26 | Webhook停机或投递遗漏 | 05每10分钟分页对账补偿；即时能力标为未启用 | 未执行 |
| ST-27 | 同根因跨新HEAD反复失败 | 持久修复预算不重置，默认3轮后阻塞，不无限修复 | 未执行 |
| ST-28 | 心跳缺失但worker仍运行 | 只标记疑似停止，09核验前不接管；移交后拒绝旧worker写入 | 未执行 |
| ST-29 | 10/11记录职责 | 只随真实变化回调，文件写锁和PR去重，不登记Cron或独立消费者 | 未执行 |
| ST-30 | 超过单轮5个变化对象 | 持久排队并保存分页检查点，不丢任务、不提前推进游标 | 未执行 |
| ST-31 | 合并候选SHA与PR HEAD不同 | API证明版本绑定且符合现有证据规则；否则证据不足 | 未执行 |
| ST-32 | 持久化接收或派发部分失败 | 不能报告已接收/已启动，按检查点安全补发，不重复会话 | 未执行 |
| ST-33 | 没有n8n、Webhook、外部DB或事件接口 | 02保存计划，03定时执行，05主动诊断并保存失败修复项，03下一轮续接，08按职责维护记录；只依赖已有Harness/GitHub能力 | 未执行 |
